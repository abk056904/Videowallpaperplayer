# BUILD A MINIMAL-RESOURCE WINDOWS 11 VIDEO WALLPAPER ENGINE

You are a senior Windows systems engineer, C++ performance engineer, DirectX graphics engineer, and multimedia-engine developer.

Your task is to **actually build** a native Windows 11 video wallpaper application in this repository.

This application is NOT intended to maximize graphical effects or GPU utilization.

Its primary objective is:

> **Use the absolute minimum practical amount of disk space, RAM, VRAM, CPU time, GPU time, threads, background activity, power, and system resources while still providing smooth video wallpaper playback.**

The application must be designed from the beginning around this principle.

---

# 1. PRIORITY ORDER

When making architectural or implementation decisions, optimize according to this priority:

```text
1. Minimum idle resource consumption
2. Minimum RAM consumption
3. Minimum CPU consumption
4. Minimum GPU consumption
5. Minimum VRAM consumption
6. Minimum application disk footprint
7. Smooth video playback
8. Fast startup
9. Reliability
10. Features
11. UI convenience
```

Do NOT sacrifice massive amounts of resources merely to make a feature slightly more convenient.

If two implementations provide equivalent functionality:

> Always choose the one that uses less memory, CPU, GPU, disk space, threads, and background activity.

---

# 2. IMPORTANT INTERPRETATION OF "HIGH PERFORMANCE"

Do NOT interpret high performance as:

> "Use the GPU as much as possible."

Instead interpret it as:

> "Achieve the required visual output using as little hardware work as possible."

For example:

```text
BAD:

4K 30 FPS video
→ decode 60 FPS
→ render 144 FPS
→ repeatedly copy textures
→ unnecessarily process every monitor refresh
```

Preferred:

```text
4K 30 FPS video
→ hardware decode at approximately 30 FPS
→ retain frame on GPU
→ present/update only when required
→ sleep when nothing needs to happen
```

The application should **not consume resources merely because resources are available**.

---

# 3. RESOURCE BUDGET

Design around explicit resource budgets.

These are targets, not fake guarantees.

## Idle / paused wallpaper

When wallpaper is paused, invisible, covered, locked, display-off, or gaming:

```text
CPU:
    ideally near 0%

GPU:
    ideally 0% rendering activity

VRAM:
    minimum necessary

RAM:
    minimum necessary

Decoder:
    stopped

Frame queue:
    empty or minimal

Render loop:
    stopped

Video decoding:
    stopped

Animation timers:
    stopped

Polling:
    avoided
```

The application should effectively become:

```text
event-driven process
+
tray icon/control
+
minimal state
```

rather than an active multimedia application.

The installed application should be as small as reasonably practical.

Do NOT bundle unnecessary frameworks.

Avoid:

* Electron
* Chromium
* WebView2 unless absolutely required
* Qt unless there is a compelling reason
* .NET runtime dependency unless unavoidable
* embedded browsers
* game engines
* large UI frameworks
* unnecessary DLLs
* duplicate codec libraries

Prefer Windows APIs already present on the system.

Primary technologies:

```text
C++20

DXGI

Windows multimedia APIs
```

Use system-provided:

```text
d3d11.dll
dxgi.dll
mfplat.dll

mfreadwrite.dll
```

where appropriate rather than shipping redundant implementations.

---

# 5. STATIC LINKING POLICY

Do NOT statically link large libraries without justification.

Static linking can dramatically increase executable size.

Evaluate:

```text
static CRT
dynamic CRT
third-party libraries
```

Choose the configuration that provides the smallest practical deployment while remaining reliable.

Do not blindly optimize executable size at the expense of requiring obscure dependencies.

Measure final:

```text
.exe size
.dll size
total installed size
```

---

# 6. NO UNNECESSARY DEPENDENCIES

Before adding a dependency ask:

```text
Can Windows provide this functionality?
Can C++ standard library provide this?
Can existing code provide this with minimal implementation?
```

If yes:

> Do not add a dependency.

Every dependency must be justified by:

```text
feature gained
size added
RAM impact
startup impact
runtime overhead
maintenance cost
```

---

# 7. MINIMAL PROCESS ARCHITECTURE

Do not create multiple processes.

Preferred:

```text
1 application process
```

Do not create:

```text
UI process
decoder process
renderer process
monitor process
```

unless Windows absolutely requires it.

Keep everything in one lightweight process.

---

# 8. MINIMAL THREAD COUNT

Do not create threads unnecessarily.

Target architecture:

```text
Main/UI thread
    ↓
Decoder worker
    ↓
Render/control worker where actually required
```

Performance monitoring should preferably be event-driven or use a low-frequency worker.

Do NOT create:

```text
1 thread per monitor
1 thread per video
1 thread per decoder
1 thread per performance metric
1 thread per playlist
```

For example:

```text
3 monitors
5 playlists
100 videos
```

must NOT result in dozens of threads.

---

# 9. THREAD LIFETIME

Threads that have nothing to do should block.

They must NOT continuously execute:

```cpp
while (running)
{
    check();
    Sleep(1);
}
```

Avoid:

```cpp
Sleep(1)
Sleep(5)
Sleep(10)
```

polling loops where an event, condition variable, waitable timer, or Windows message can be used.

Preferred:

```text
worker
  ↓
wait
  ↓
event occurs
  ↓
wake
  ↓
perform work
  ↓
wait again
```

---

# 10. ZERO-BUSY-WAIT POLICY

This is mandatory.

Do not write continuous loops that consume CPU while waiting.

Bad:

```cpp
while (running)
{
    if (frameReady)
        render();
}
```

Bad:

```cpp
while (running)
{
    checkGame();
    checkGPU();
    checkCPU();
}
```

Preferred:

```text
Windows event
condition_variable
waitable timer
message
notification
callback
```

Use polling only when there is genuinely no suitable event-driven API.

---

# 11. RAM IS A PRIMARY OPTIMIZATION TARGET

Minimize RAM aggressively.

Do not preload videos.

Do not cache complete videos.

Do not decode entire files.

Do not maintain large frame queues.

Do not duplicate video frames.

Do not create multiple copies of metadata.

Do not keep unused decoder instances alive.

Do not keep unnecessary thumbnails in memory.

Do not keep entire playlists as large objects.

---

# 12. FRAME QUEUE

Use a very small bounded queue.

Start with:

```text
2–3 frames
```

and benchmark.

Do NOT automatically use:

```text
30 frames
60 frames
120 frames
```

because that can consume hundreds of MB for high-resolution video.

Example:

4K RGBA frame:

```text
3840 × 2160 × 4
≈ 33 MB
```

Even several unnecessary copies become expensive.

For this reason:

> Avoid CPU-side 4K frame buffers whenever possible.

---

# 13. GPU FRAME STORAGE

Keep decoded frames on the GPU where possible.

Preferred:

```text
hardware decoder
       ↓
DXGI/D3D11 GPU surface
       ↓
shader
       ↓
render
```

Avoid:

```text
GPU decoder
↓
GPU → CPU
↓
CPU frame
↓
CPU conversion
↓
CPU → GPU
↓
render
```

Every unnecessary copy costs:

* CPU
* RAM
* PCIe/bus bandwidth
* latency
* power

---

# 14. HARDWARE DECODING

Hardware decoding is required whenever available because the goal is minimum CPU consumption.

Preferred:

```text
H.264 → hardware decoder
HEVC → hardware decoder
AV1 → hardware decoder
VP9 → hardware decoder
```

But do not blindly enable hardware decoding if it increases overall resource consumption due to an inefficient implementation.

Measure:

```text
CPU
GPU video decode engine
VRAM
RAM
power
```

Choose the efficient path.

---

# 15. DO NOT OVERUSE GPU

Hardware acceleration does NOT mean:

> Render unnecessarily at maximum GPU frequency.

The wallpaper should generate only the work necessary to display the video.

For example:

```text
Video = 24 FPS
Monitor = 240 Hz
```

Do not perform 240 full rendering operations per second merely because the monitor is 240 Hz.

Use frame pacing intelligently.

---

# 16. SOURCE FPS AWARENESS

Determine:

```text
source FPS
monitor refresh rate
```

Examples:

```text
24 FPS video
60 Hz monitor

30 FPS video
144 Hz monitor

60 FPS video
165 Hz monitor
```

Schedule frame presentation intelligently.

Do not create unique work for refresh cycles where the video frame has not changed.

---

# 17. STATIC FRAME OPTIMIZATION

If the current frame remains unchanged:

> Do not unnecessarily redraw it.

When paused:

```text
do not redraw
```

When the desktop wallpaper is occluded:

```text
do not redraw
```

When the monitor is unavailable:

```text
do not redraw
```

---

# 18. OCCLUSION / VISIBILITY

Detect when the wallpaper is not useful.

Possible states:

```text
VISIBLE
PARTIALLY_VISIBLE
COVERED
FULLSCREEN_APP
GAME
LOCKED
DISPLAY_OFF
SUSPENDED
USER_PAUSED
```

When wallpaper cannot be seen:

```text
stop frame scheduling
stop decoder advancement
stop GPU rendering
```

Do not merely hide the rendered window while continuing playback.

---

# 19. FULLSCREEN APPLICATION

If a fullscreen application covers the monitor:

```text
pause wallpaper
```

This includes:

* games
* video players
* fullscreen browsers
* presentations
* other fullscreen applications

Do not pause for ordinary maximized windows unless configured.

---

# 20. GAME DETECTION

Game detection must be extremely lightweight.

Do not scan all processes continuously.

Preferred strategy:

```text
foreground window change
        ↓
identify process
        ↓
inspect process only when needed
        ↓
determine game/fullscreen status
```

Cache results.

Do not repeatedly perform expensive process inspection for the same process.

---

# 21. GAME PROCESS CACHE

Maintain a small cache:

```text
process ID
executable path
classification
last checked time
```

If the same process remains foreground:

> Do not repeatedly perform expensive analysis.

Invalidate the cache when:

```text
process exits
foreground process changes
user changes configuration
```

---

# 22. WORKLOAD MONITORING

The workload monitor must itself consume very little CPU.

Do not check CPU/GPU usage every millisecond.

A reasonable starting point:

```text
sample approximately once per 1–2 seconds
```

Then profile.

This is enough for wallpaper pausing.

There is no need to detect a workload spike within 10 milliseconds.

---

# 23. WORKLOAD DETECTION

Monitor:

```text
CPU utilization
GPU utilization
GPU memory
system RAM
foreground process
fullscreen state
game state
battery state
display state
lock state
```

But do not collect all metrics continuously if they aren't required.

If the system is already in:

```text
GAME
FULLSCREEN
LOCKED
DISPLAY_OFF
```

there may be no reason to aggressively monitor other workload metrics.

---

# 24. STATE MACHINE

Implement a central state machine.

Example:

```text
                    ┌───────────────┐
                    │    PLAYING    │
                    └───────┬───────┘
                            │
            ┌───────────────┼────────────────┐
            │               │                │
         GAME           FULLSCREEN       HIGH LOAD
            │               │                │
            └───────────────┼────────────────┘
                            ↓
                    ┌───────────────┐
                    │    PAUSED     │
                    └───────┬───────┘
                            │
                     conditions clear
                            ↓
                    ┌───────────────┐
                    │    RESUME     │
                    └───────────────┘
```

Do not allow independent subsystems to start/stop the decoder directly.

Use one central controller.

---

# 25. PAUSE REASONS

Use a bitmask or equivalent compact state:

```cpp
enum class PauseReason : uint32_t
{
    None            = 0,
    User            = 1 << 0,
    Game            = 1 << 1,
    Fullscreen      = 1 << 2,
    HighCPU         = 1 << 3,
    HighGPU         = 1 << 4,
    HighMemory      = 1 << 5,
    Battery         = 1 << 6,
    Locked          = 1 << 7,
    DisplayOff      = 1 << 8,
    MonitorHidden   = 1 << 9
};
```

If ANY required reason exists:

```text
PAUSED
```

Only resume when all relevant reasons clear.

---

# 26. HYSTERESIS

Avoid oscillation.

Example:

```text
GPU pause threshold = 90%
GPU resume threshold = 70%
```

CPU:

```text
pause = 85%
resume = 65%
```

Memory:

```text
pause = 90%
resume = 75%
```

---

# 27. DELAYED PAUSE

Do not pause because of a momentary spike.

Example:

```text
GPU > 90%
```

must persist:

```text
3 seconds
```

before pausing.

Likewise resume:

```text
GPU < 70%
```

for:

```text
5 seconds
```

Make values configurable.

---

# 28. IMMEDIATE PAUSE CONDITIONS

Some conditions should override the delay:

```text
Windows locked
Display off
User explicitly paused
System suspended
```

These should immediately stop unnecessary work.

---

# 29. WHEN PAUSED, RELEASE MORE RESOURCES

Do not simply set:

```cpp
playing = false;
```

and leave everything running.

When entering a long pause:

1. Stop decoder advancement.
2. Stop render scheduling.
3. Clear unnecessary frame buffers.
4. Release temporary GPU resources.
5. Release next-video decoder.
6. Keep only minimal state.
7. Keep playlist/configuration metadata.
8. Wait for resume event.

If the wallpaper is likely to remain paused for a long time, consider releasing decoder resources completely.

---

# 30. LONG-TERM PAUSE

Differentiate:

```text
short pause
```

from:

```text
long pause
```

For example:

```text
Pause < 5 seconds:
    keep minimal resources for fast resume

Pause > configurable duration:
    release decoder and temporary GPU resources
```

This minimizes RAM/VRAM while avoiding unnecessary initialization churn.

---

# 31. VIDEO TRANSITION MEMORY

When playing:

```text
Video A
```

and preparing:

```text
Video B
```

do not fully instantiate two complete pipelines unless required.

Keep the next-video preparation minimal.

Preferred:

```text
Current:
    active decoder

Next:
    metadata/source preparation

Transition:
    initialize decoder
```

Only maintain simultaneous decoders if profiling proves that the transition improvement is worth the additional RAM/VRAM.

---

# 32. PLAYLIST MEMORY

A playlist of 10,000 videos should still use very little RAM.

Store:

```text
path
small metadata
flags
```

Do not store:

```text
full decoded thumbnails
video frames
decoder objects
GPU textures
```

for every item.

---

# 33. THUMBNAIL SYSTEM

The UI library should not consume hundreds of MB for thumbnails.

Use:

```text
small thumbnail resolution
disk cache
LRU memory cache
```

Example:

```text
maximum in-memory thumbnails = 50
```

or determine dynamically.

When UI closes:

> Release thumbnail memory aggressively.

The wallpaper engine must not keep the entire UI library in RAM.

---

# 34. UI PROCESSING

The UI should not perform:

* video decoding
* rendering
* performance polling
* thumbnail generation synchronously
* filesystem scans continuously

When the UI is closed/minimized to tray:

> Stop expensive UI work.

The wallpaper engine should continue independently.

---

# 35. UI TECHNOLOGY

Choose the smallest practical native UI technology.

If a Win32 UI is sufficient:

> Prefer Win32.

Do not introduce a large UI framework merely to create:

* buttons
* lists
* settings
* tray menu

If a modern UI technology is used, measure its memory overhead.

---

# 36. STARTUP

Optimize startup time.

Startup sequence should be:

```text
process starts
↓
minimal initialization
↓
load configuration
↓
discover monitors
↓
create wallpaper host
↓
initialize decoder
↓
play
```

Do NOT:

```text
start application
↓
scan entire video library
↓
generate 5,000 thumbnails
↓
load all metadata
↓
initialize every monitor
↓
finally display wallpaper
```

Only initialize what is necessary.

---

# 37. LAZY INITIALIZATION

Use lazy loading.

Examples:

```text
UI:
    initialize only when opened

Playlist:
    load only required metadata

Thumbnail:
    generate only when displayed

Decoder:
    create only when playback begins

Monitor:
    initialize only when active

Next video:
    prepare only when needed
```

---

# 38. LIBRARY SCANNING

If a folder contains thousands of videos:

Do not scan it repeatedly.

Use:

* filesystem notifications
* cached metadata
* modification timestamps
* file size
* lightweight database/index if actually necessary

Avoid rescanning the entire library every startup if it is unnecessary.

---

# 39. DISK CACHE

Any disk cache must have a size limit.

Example:

```text
thumbnail cache:
    maximum 100 MB
```

Prefer a much smaller default if practical.

Implement:

```text
LRU eviction
```

Never allow caches to grow forever.

---

# 40. LOG FILE SIZE

Logs must also be bounded.

Example:

```text
current.log
previous.log
```

Maximum total:

```text
5–10 MB
```

Do not create hundreds of MB of logs.

---

# 41. CONFIGURATION SIZE

Configuration should remain tiny.

Do not store:

* thumbnails
* video data
* cached frames
* unnecessary statistics

Use a compact human-readable configuration.

---

# 42. NO DATABASE UNLESS NEEDED

Do not add SQLite merely because it is convenient.

If a simple configuration/index file is sufficient:

> Use the simple file.

Every dependency must justify its runtime and disk footprint.

---

# 43. GPU RESOURCE BUDGET

Use as little VRAM as possible.

Avoid duplicate textures.

For one monitor:

```text
current frame
+
minimal intermediate resource
```

should generally be sufficient.

For multiple monitors showing the same video:

> Do not decode the same video independently for every monitor unless necessary.

Prefer:

```text
ONE decoder
      ↓
shared decoded frame
      ↓
Monitor 1 renderer
Monitor 2 renderer
Monitor 3 renderer
```

when the monitors share the same wallpaper.

---

# 44. SHARED PLAYBACK

If:

```text
Monitor 1 = same video
Monitor 2 = same video
Monitor 3 = same video
```

do not create:

```text
3 decoders
3 frame queues
3 copies of the video
```

Prefer:

```text
one decoder
one playback timeline
one decoded frame
multiple lightweight presentations
```

This is a major optimization.

---

# 45. INDEPENDENT PLAYBACK

If monitors use different videos:

```text
Monitor 1 → A
Monitor 2 → B
Monitor 3 → C
```

use separate decoders only where required.

Still:

* share the D3D device
* share device resources
* avoid duplicated infrastructure
* keep queues tiny

---

# 46. SAME VIDEO, DIFFERENT MONITOR RESOLUTIONS

If one video is displayed on:

```text
4K
1440p
1080p
```

do not decode three copies.

Decode once.

Scale independently in GPU shaders.

---

# 47. VIDEO LOOP OPTIMIZATION

When looping the same video:

Do not repeatedly recreate the entire application-level playback system.

Reuse:

* decoder where possible
* GPU resources
* metadata
* textures

Reset only the playback state required.

---

# 48. CODEC-SPECIFIC EFFICIENCY

Detect codec before selecting playback strategy.

Use hardware decoding for supported codecs.

If a codec cannot be hardware decoded:

```text
software fallback
```

But clearly report:

```text
Software decoding
```

because CPU consumption may be significantly higher.

---

# 49. 4K/8K CONSIDERATION

Do not assume every machine can efficiently handle 8K.

Detect:

```text
resolution
FPS
codec
hardware decode capability
```

If the video is excessive for the hardware:

* report it
* avoid unnecessary scaling
* avoid buffering huge amounts
* gracefully handle decoder limitations

Do not solve high-resolution playback by allocating enormous RAM buffers.

---

# 50. FRAME DROPPING

For wallpaper playback:

> Low latency is more important than preserving every frame.

If the decoder is behind:

```text
drop obsolete frames
```

instead of allowing:

```text
frame queue → 10 → 20 → 50 → 100
```

which creates increasing latency and memory usage.

---

# 51. BACKPRESSURE

Implement backpressure.

If frame queue is full:

```text
decoder must not endlessly produce frames
```

It should block or discard obsolete frames appropriately.

Never allow unlimited producer/consumer growth.

---

# 52. NO UNNECESSARY COPY

Audit every frame transition:

```text
decoder
→ frame
→ queue
→ renderer
→ shader
→ output
```

Document whether each step is:

```text
CPU copy
GPU copy
reference
shared surface
```

The goal is:

> Minimum number of memory transfers.

---

# 53. COM OBJECT MANAGEMENT

Use:

```cpp
Microsoft::WRL::ComPtr
```

or equivalent RAII.

Every COM interface must have clear ownership.

Check for:

* reference cycles
* retained device contexts
* retained textures
* Media Foundation objects not released

A single retained GPU resource can keep significant VRAM alive.

---

# 54. RESOURCE LIFETIME

Resources should have explicit lifetimes:

```text
Application lifetime:
    D3D device
    core configuration

Playback lifetime:
    decoder
    current video resources

Frame lifetime:
    current frame

UI lifetime:
    thumbnails
    UI controls

Monitor lifetime:
    monitor-specific resources
```

Do not keep playback resources alive when no playback exists.

---

# 55. IDLE RESOURCE MODE

Create a distinct:

```text
LOW_RESOURCE_MODE
```

When active:

```text
decoder stopped
renderer stopped
frame queue empty
GPU work stopped
monitor polling minimized
```

The process should behave almost like a dormant control application.

---

# 56. SMART RESUME

When the system resumes:

Do not immediately perform expensive work repeatedly.

Use:

```text
one resume event
```

then initialize.

Avoid:

```text
resume
→ fail
→ retry 1
→ retry 2
→ retry 3
```

in a tight loop.

Use controlled retry delays.

---

# 57. ERROR RECOVERY MUST ALSO BE LOW-RESOURCE

Do not create a recovery loop that consumes CPU.

Bad:

```text
while (decoderFailed)
{
    recreateDecoder();
}
```

Preferred:

```text
failure
↓
release resources
↓
schedule retry
↓
wait
↓
retry
```

---

# 58. POWER EFFICIENCY

Resource efficiency also means power efficiency.

Avoid unnecessary:

* wakeups
* timers
* GPU submissions
* CPU polling
* memory transfers

The application should be friendly to:

* laptops
* battery-powered systems
* integrated GPUs

---

# 59. INTEGRATED GPU CONSIDERATION

On laptops with integrated graphics:

> Prefer the lowest-power graphics path capable of smooth playback.

Do not force a discrete GPU merely because it exists.

Avoid architectures that unnecessarily wake a high-power NVIDIA/AMD GPU for a simple wallpaper.

---

# 60. GPU ADAPTER SELECTION

Detect adapters and outputs.

Determine:

```text
monitor
→ associated adapter
→ video decode capabilities
```

Prefer efficient adapter selection.

Do not automatically select the most powerful GPU.

---

# 61. PERFORMANCE SAMPLING ITSELF

The performance monitor must not become a performance problem.

Do not collect hundreds of counters every second.

Only collect metrics needed for:

```text
pause decisions
diagnostics
UI
```

The UI can use a slower update rate:

```text
1–2 updates/sec
```

rather than 60 updates/sec.

# 62. UI PERFORMANCE PANEL

When the UI is closed:

```text
stop updating performance graphs
```

When opened:

```text
sample statistics
```

Do not keep high-frequency monitoring active solely for a hidden graph.

---

# 63. DEBUG BUILD VS RELEASE

Debug builds may have:

* assertions
* Direct3D debug layer
* verbose logging
* diagnostics

Release:

```text

```

# 64. COMPILER OPTIMIZATION

Use appropriate MSVC Release optimizations.

Consider:

```text
/O2
/LTCG where beneficial
/GL where appropriate
```

Do not enable options blindly.

Benchmark before and after.

---

# 65. ALLOCATIONS

Minimize allocations in the playback loop.

Do NOT allocate/deallocate every frame.

Bad:

```cpp
renderFrame()
{
    std::vector<uint8_t> buffer(...);
    ...
}
```

Preferred:

```text
allocate persistent resources
reuse them
```

The steady-state playback loop should have extremely low allocation activity.

---

# 66. STRING ALLOCATIONS

Avoid unnecessary string creation in hot paths.

Do not repeatedly construct:

```text
std::wstring
std::filesystem::path
```

during every frame.

Paths and metadata are not frame-rate data.

Cache them.

---

# 67. HOT PATH AUDIT

Identify these hot paths:

```text
decoder
frame queue
frame scheduling
render
performance sampling
```

For each, measure:

```text
allocations
locks
copies
system calls
CPU time
GPU submissions
```

Optimize only after measurement.

---

# 68. RENDER LOOP TARGET

The render loop must be extremely small.

Conceptually:

```cpp
waitUntilFrameNeeded();

if (paused)
    return;

if (!frameAvailable)
    return;

renderCurrentFrame();
```

Avoid putting:

* filesystem operations
* process enumeration
* configuration loading
* logging
* thumbnail generation
* playlist scanning

inside the render loop.

---

# 69. DECODER LOOP TARGET

Decoder should:

```text
wait for demand
decode next required frame
place/share frame
wait again
```

Do not decode dozens of frames ahead.

---

# 70. PLAYBACK CLOCK

Use a monotonic high-resolution clock.

Do not depend on wall-clock time.

Use:

```text
QueryPerformanceCounter
```

or an appropriate C++/Windows abstraction.

Handle:

* pause
* resume
* seeking
* loop
* dropped frames

without clock drift.

---

# 71. AUDIO

Default:

```text
Audio disabled
```

Do not initialize audio playback APIs unless audio is explicitly requested.

A wallpaper player normally does not need:

* audio decoder
* audio renderer
* audio buffer
* audio thread

This reduces resource usage.

---

# 72. VIDEO METADATA

Read metadata lazily.

At startup, only obtain:

```text
duration
resolution
FPS
codec
```

Do not perform expensive analysis of every video.

Advanced metadata should be obtained only when required.

---

# 73. LIBRARY DATABASE

If a library index becomes necessary, make it:

* compact
* lazy
* incremental
* bounded

Do not store unnecessary duplicate metadata.

---

# 74. FILESYSTEM ACTIVITY

The wallpaper playback path should not repeatedly touch the filesystem.

Once playback begins:


# 93. RESOURCE GOVERNOR

Create a central component:

```cpp

```

Its job is to decide the application's resource state.

Example:

```text

```

This is preferable to having five different systems independently manipulating resources.

# 95. RESOURCE STATE TRANSITIONS

The final implementation should be optimized around one fundamental principle:

If the user cannot see the wallpaper:

# "DO NO WORK."

If the wallpaper is paused:

# "DO NO VIDEO WORK."

# "DO NOT REDRAW IT."

# "DO NOT DECODE IT TWICE."

# "USE THE EVENT."

If a resource is no longer needed:

# "RELEASE IT."
