# TASK: Build a High-Performance Windows 11 Video Wallpaper Engine

You are an autonomous senior C++/Windows graphics engineer.

Your task is to **actually implement** a production-quality Windows 11 video wallpaper application in the current repository.

Do not merely provide recommendations, pseudocode, architecture diagrams, or snippets.

You must:

* inspect the existing repository
* inspect the installed Windows SDK/compiler/toolchain
* create the required source files
* compile the project
* run tests
* fix compilation/linking/runtime errors
* profile important paths
* optimize based on measurements
* leave the repository in a buildable state

The application must prioritize:

> **Very low CPU usage + hardware video decoding + efficient GPU rendering + near-zero resource usage when paused/invisible.**

---

# 1. NON-NEGOTIABLE REQUIREMENTS

The final application must:

1. Run natively on Windows 11.
2. Be x64.
3. Use C++20 or newer.
4. Use native Win32 APIs.
5. Use Direct3D 11 for the initial renderer unless there is a demonstrated technical reason to use D3D12.
6. Use Windows Media Foundation for video playback/decoding where practical.
7. Prefer hardware video decoding.
8. Render video frames directly into GPU textures.
9. Avoid unnecessary CPU↔GPU frame copies.
10. Support multiple monitors.
11. Support independent wallpaper/playlists per monitor.
12. Support video playlists.
13. Support loop modes.
14. Support shuffle.
15. Automatically pause during games/fullscreen/high workloads.
16. Automatically resume afterward.
17. Stop decoding when playback is paused.
18. Stop rendering when wallpaper cannot be seen.
19. Avoid busy loops.
20. Remain stable for 24+ hours of continuous operation.
21. Recover from monitor changes and common GPU/decoder failures.
22. Store configuration persistently.
23. Provide a system-tray application.
24. Start with Windows optionally.
25. Provide useful diagnostics and performance information.

---

# 2. DO NOT USE THESE ARCHITECTURES

Do NOT use:

* Electron
* Chromium
* WebView-based rendering
* HTML/CSS wallpaper rendering
* Unity
* Unreal Engine
* a game engine
* Python as the playback engine
* Java
* continuously polling every few milliseconds
* a CPU-based frame conversion pipeline
* decoding every frame into a CPU bitmap and uploading it to the GPU
* unnecessary third-party frameworks

The application must be a **native Windows graphics application**.

# 12. GPU RESOURCE STRATEGY

Avoid repeatedly creating textures.

Use resource pools where practical.

Do not:

```text
create texture
render
destroy texture
create texture
render
destroy texture
```

for every frame.

Instead:

```text
initialize resources
reuse resources
release when video/monitor changes
```

Keep GPU resources lifetime-managed with RAII.

Use:

```cpp
Microsoft::WRL::ComPtr<T>
```

or another appropriate RAII strategy.

No raw COM ownership leaks.

---

# 13. VIDEO FRAME PIPELINE

Create a bounded frame queue.

Example:

```text
Decoder Thread
      │
      ▼
┌───────────────┐
│ Frame Queue   │
│ max N frames  │
└───────┬───────┘
        │
        ▼
Render Thread
```

The queue must have a hard upper bound.

Do not allow unlimited buffering.

Do not load entire videos into memory.

A reasonable starting point is approximately 2–5 frames, then profile.

If the renderer is behind:

* drop obsolete frames where appropriate
* do not allow latency to grow indefinitely

For a wallpaper, current-frame freshness is more important than preserving every frame.

# 14. FRAME TIMING

Use high-resolution timing.

Use appropriate Windows timing facilities such as:

* QueryPerformanceCounter
* waitable timers
* synchronization primitives

Do not use:

```cpp
while (true) {
    if (timeToRender()) {
        render();
    }
}
```

This creates unnecessary CPU usage.

Instead, the render thread should sleep/block until:

```text
next frame deadline
OR
new frame available
OR
pause requested
OR
shutdown requested
OR
monitor change
```

# 66. MOST IMPORTANT PERFORMANCE RULE

The application is NOT considered high-performance merely because it uses Direct3D.

The implementation must actively minimize unnecessary work.

Follow this rule throughout the code:

```text
IF the user cannot see the wallpaper:
    do not render

IF playback is paused:
    do not decode

IF there is no new frame:
    do not render a new frame

IF the source video is 30 FPS:
    do not decode 144 FPS

IF hardware decoding is available:
    use it

IF a frame can remain on the GPU:
    keep it on the GPU

IF an event can replace polling:
    use the event

IF a worker has nothing to do:
    block/sleep

IF a resource is no longer needed:
    release it
```

The final product should behave like a **dedicated lightweight wallpaper engine**, not like a game engine continuously rendering an animated scene.
