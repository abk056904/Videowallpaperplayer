# PROJECT: ULTRA-LOW-RESOURCE WINDOWS 11 VIDEO WALLPAPER ENGINE

You are a senior Windows systems engineer, C++ performance engineer,
Direct3D 11 engineer, Media Foundation engineer, multimedia engineer,
and Windows desktop application developer.

Your task is to DESIGN, IMPLEMENT, BUILD, TEST, PROFILE, AND OPTIMIZE
a native Windows 11 video wallpaper application.

Do not merely provide an architecture or tutorial.

You must actually inspect the repository, create the project, implement
the application, compile it, test it, diagnose errors, and optimize it.

============================================================
# 1. FUNDAMENTAL OBJECTIVE
============================================================

The application's PRIMARY purpose is:

    Play video files as animated Windows 11 desktop wallpapers.

Its PRIMARY engineering objective is:

    MINIMUM PRACTICAL RESOURCE CONSUMPTION.

The application must use as little as reasonably possible:

    - RAM
    - CPU
    - GPU
    - VRAM
    - disk space
    - CPU wakeups
    - threads
    - handles
    - filesystem I/O
    - GPU memory transfers
    - CPU↔GPU copies
    - background activity
    - power/battery

while maintaining smooth, reliable video playback.

IMPORTANT:

Do NOT interpret "high performance" as:

    "use as much CPU/GPU as possible."

Interpret it as:

    "produce the required visual output with the least amount of
     hardware work possible."

The application should never consume resources simply because
those resources are available.

The fundamental optimization principle is:

    DO THE LEAST AMOUNT OF WORK NECESSARY TO DISPLAY THE CURRENT FRAME.

And:

    IF THE USER CANNOT SEE THE WALLPAPER, DO ALMOST NO VIDEO WORK.

And:

    IF THE CURRENT VIDEO FRAME HAS NOT CHANGED, DO NOT REDRAW IT
    UNNECESSARILY.

And:

    IF PLAYBACK IS PAUSED, STOP THE DECODER AND RENDERER WHEN
    PRACTICAL.

============================================================
# 2. TECHNOLOGY DECISION
============================================================

Use a NATIVE C++ implementation.

Preferred:

    C++20 or newer
    MSVC
    Windows 11 SDK
    Win32
    Direct3D 11
    DXGI
    Media Foundation
    Windows APIs

Do NOT use:

    Electron
    Chromium
    WebView2
    Unity
    Unreal Engine
    Qt
    Avalonia
    WPF
    WinUI runtime as the core engine
    .NET runtime
    Java
    Python
    JavaScript runtime

unless there is an extremely strong technical reason.

The application should preferably be a single native executable
with only the minimum required Windows/system dependencies.

The reason for avoiding large frameworks is NOT that they are
necessarily slow.

The reason is that this application has an unusually strict
resource-footprint objective.

============================================================
# 3. UI TECHNOLOGY
============================================================

Use native Win32 for the UI unless there is a compelling reason
to use something else.

The UI only needs to provide:

    - playlist management
    - video library management
    - wallpaper selection
    - monitor selection
    - playback settings
    - performance settings
    - pause behavior
    - game detection settings
    - fullscreen detection settings
    - battery behavior
    - system tray controls

The UI must NOT be responsible for:

    - video decoding
    - frame scheduling
    - GPU rendering
    - performance monitoring at high frequency
    - wallpaper rendering
    - video frame buffering

The UI must be separable from the playback engine.

When the settings window is closed:

    release UI-specific resources.

Do not keep unnecessary UI resources alive.

============================================================
# 4. TARGET APPLICATION MODEL
============================================================

The application should behave like a lightweight background
Windows component.

Normal operation:

    Windows
       |
       +---- Native wallpaper engine
                  |
                  +---- Media Foundation
                  |
                  +---- D3D11
                  |
                  +---- DXGI
                  |
                  +---- Win32 wallpaper host
                  |
                  +---- Resource Governor

There should NOT be:

    one process per monitor
    one process per video
    one process per decoder
    one process for performance monitoring
    one process for the UI
    background Windows service

Prefer:

    ONE native process.

============================================================
# 5. NO WINDOWS SERVICE
============================================================

Do not create a Windows Service.

The wallpaper engine should be a normal user application.

When the user exits the application:

    all resources are released
    wallpaper state is cleaned up
    process terminates

Do not leave a hidden service running.

============================================================
# 7. CORE RESOURCE STATES
============================================================

Implement an explicit resource state machine.

At minimum:

    ACTIVE
    REDUCED
    PAUSED
    SUSPENDED

ACTIVE:

    normal video playback.

REDUCED:

    minimize optional work while maintaining playback if possible.

PAUSED:

    stop video decoding/frame advancement and rendering when
    the wallpaper does not need to change.

SUSPENDED:

    release decoder and temporary resources if the pause is
    expected to last for a significant amount of time.

Example:

    ACTIVE
       |
       +---- game detected
       |
       +---- fullscreen detected
       |
       +---- high system workload
       |
       v
    PAUSED
       |
       +---- long pause
       |
       v
    SUSPENDED

Resume:

    SUSPENDED
       |
       v
    recreate minimal playback resources
       |
       v
    ACTIVE

============================================================
# 8. RESOURCE GOVERNOR
============================================================

Create:

    ResourceGovernor

It must be the central authority for deciding whether playback
should be active.

Do NOT allow five unrelated subsystems to independently start
and stop the decoder.

Use centralized state.

Example pause reasons:

    USER
    GAME
    FULLSCREEN
    HIGH_CPU
    HIGH_GPU
    HIGH_MEMORY
    BATTERY
    LOCKED
    DISPLAY_OFF
    WALLPAPER_HIDDEN
    SYSTEM_SUSPENDED

Represent these efficiently, for example using a bitmask.

Playback is allowed only when the relevant pause reasons are clear.

============================================================
# 9. GAME DETECTION
============================================================

The application must automatically detect when a game or
high-workload application is running.

The objective is:

    stop wallpaper resource consumption during gaming.

However, game detection itself must consume almost no resources.

DO NOT continuously enumerate every process.

DO NOT do this:

    every 100 ms:
        enumerate all processes
        inspect every executable
        calculate CPU usage

Instead:

    detect foreground-window changes
            |
            v
    identify foreground process
            |
            v
    inspect only the relevant process
            |
            v
    classify/cache result

Cache process classification.

Invalidate cache when:

    process exits
    foreground process changes
    configuration changes

============================================================
# 10. FULLSCREEN DETECTION
============================================================

Detect fullscreen applications.

If a fullscreen application covers the wallpaper:

    stop wallpaper playback.

This should include:

    games
    fullscreen video players
    presentations
    fullscreen browsers
    other fullscreen applications

Do not continuously perform expensive fullscreen calculations.

Use window/foreground state changes where possible.

============================================================
# 11. HIGH CPU/GPU WORKLOAD DETECTION
============================================================

Optionally pause playback when system workload becomes high.

Monitor only what is necessary.

Possible metrics:

    CPU utilization
    GPU utilization
    memory pressure
    foreground application
    fullscreen state
    game state

Do NOT poll at extremely high frequency.

A starting target:

    approximately once every 1–2 seconds

Then benchmark.

The monitoring system itself must not become a resource problem.

============================================================
# 12. HYSTERESIS
============================================================

Avoid rapidly switching:

    PLAY
    PAUSE
    PLAY
    PAUSE

Use hysteresis.

Example:

    CPU pause threshold:
        85%

    CPU resume threshold:
        65%

    GPU pause threshold:
        90%

    GPU resume threshold:
        70%

Require the threshold to remain exceeded for a configurable
duration before changing state.

Example:

    pause after 3 seconds above threshold

    resume after 5 seconds below threshold

Make these configurable.

============================================================
# 13. IMMEDIATE PAUSE CONDITIONS
============================================================

The following should cause immediate or near-immediate suspension:

    Windows locked
    display off
    system sleep
    user manually paused
    wallpaper no longer visible
    fullscreen/game mode

Do not wait several seconds for these conditions.

============================================================
# 14. MEDIA FOUNDATION
============================================================

Use Windows Media Foundation as the primary video playback/
decoding pipeline.

Prefer hardware decoding where supported.

Target codecs:

    H.264
    HEVC/H.265
    AV1
    VP9

Support common containers:

    MP4
    MKV
    WebM

where Media Foundation/system codecs support them.

Do not bundle an enormous third-party codec framework simply
because it is convenient.

Use the Windows media stack where practical.

============================================================
# 15. HARDWARE DECODING
============================================================

Hardware decoding is preferred.

The desired path is conceptually:

    video file
       |
       v
    Media Foundation
       |
       v
    hardware decoder
       |
       v
    D3D11/DXGI-compatible surface
       |
       v
    GPU texture
       |
       v
    minimal shader
       |
       v
    wallpaper

Avoid:

    decoder
       |
       v
    CPU frame
       |
       v
    CPU color conversion
       |
       v
    CPU memory copy
       |
       v
    GPU upload
       |
       v
    rendering

unless absolutely necessary.

Every CPU↔GPU transfer must be justified.

============================================================
# 16. GPU MEMORY
============================================================

Minimize VRAM usage.

Do NOT:

    decode dozens of frames ahead
    duplicate textures
    create unnecessary intermediate render targets
    keep old video textures alive
    maintain multiple copies of the same frame

Keep the frame queue extremely small.

Start with approximately:

    2–3 frames

and benchmark.

Do not automatically increase buffering because more buffering
"feels safer."

For wallpaper playback, low latency is less important than
resource efficiency.

============================================================
# 17. FRAME BUFFERING
============================================================

Implement a bounded frame queue.

Never allow:

    unlimited frames
    growing queue
    unbounded producer/consumer backlog

If the decoder gets ahead:

    stop/block production or discard obsolete frames.

If playback falls behind:

    drop obsolete frames rather than accumulating latency.

For wallpaper playback:

    newest useful frame > preserving every old frame.

============================================================
# 18. RAM OPTIMIZATION
============================================================

RAM is one of the most important optimization targets.

DO NOT:

    preload complete videos
    decode complete videos
    preload entire playlists into large objects
    cache every thumbnail
    keep multiple full-resolution CPU frame copies
    keep inactive decoders alive
    keep old video resources alive unnecessarily

Example:

A 3840×2160 RGBA frame is approximately:

    3840 × 2160 × 4
    ≈ 33 MB

Therefore, several unnecessary copies can consume hundreds
of megabytes very quickly.

Avoid CPU-side 4K frame copies wherever possible.

============================================================
# 19. FRAME COPY AUDIT
============================================================

Document the path:

    decoder
      ->
    frame
      ->
    queue
      ->
    renderer
      ->
    shader
      ->
    display

For every transition determine whether it is:

    reference
    shared surface
    GPU copy
    CPU copy

Minimize copies.

The final implementation should have the fewest practical
memory transfers.

============================================================
# 20. DIRECT3D 11
============================================================

Use Direct3D 11 for rendering unless profiling proves another
native API is substantially better for this application.

Reuse:

    D3D11 device
    device context
    DXGI factory
    shaders
    sampler states
    rasterizer state
    common GPU resources

Do not recreate them every frame.

============================================================
# 21. RENDER LOOP
============================================================

The render loop must NOT run continuously at maximum speed.

Do NOT do:

    while (running)
        render();

Do NOT render at:

    240 FPS
    360 FPS
    1000 FPS

just because the monitor supports it.

If the source video is:

    24 FPS

there is no reason to perform 240 unique video rendering
operations every second.

Use intelligent frame scheduling.

============================================================
# 22. SOURCE FPS AWARENESS
============================================================

Detect:

    source FPS
    monitor refresh rate

Examples:

    24 FPS video on 60 Hz display
    30 FPS video on 144 Hz display
    60 FPS video on 165 Hz display

Schedule presentation according to the actual video frame timing.

Do not decode or process frames that cannot contribute to the
visible output.

============================================================
# 23. STATIC FRAME OPTIMIZATION
============================================================

If the current frame has not changed:

    do not unnecessarily redraw it.

When paused:

    do not continuously redraw.

When wallpaper is completely covered:

    do not continuously redraw.

When display is off:

    do not render.

When game is active:

    do not render.

============================================================
# 24. NO BUSY WAITING
============================================================

This is mandatory.

Do NOT use:

    while(true)
    while(running)
    Sleep(1)
    Sleep(5)
    Sleep(10)

as the primary synchronization strategy.

Do not continuously poll.

Use:

    Windows events
    condition variables
    waitable timers
    message queues
    callbacks
    synchronization primitives
    Media Foundation events

Workers that have nothing to do should BLOCK.

Desired behavior:

    worker
       |
       v
    wait
       |
       v
    event
       |
       v
    wake
       |
       v
    perform necessary work
       |
       v
    wait again

============================================================
# 25. THREAD COUNT
============================================================

Use as few threads as practical.

Do not create:

    one thread per monitor
    one thread per video
    one thread per playlist
    one thread per performance counter

A small architecture such as:

    UI/main thread
    decoder worker where required
    minimal control/monitoring worker

is preferable.

Measure the actual thread count.

============================================================
# 26. THREAD IDLE BEHAVIOR
============================================================

Idle threads must block.

They must not consume CPU while waiting.

When playback is paused:

    decoder worker should sleep/block.

When the application is suspended:

    unnecessary workers should terminate or block.

============================================================
# 27. ALLOCATION POLICY
============================================================

The playback hot path must have extremely low allocation activity.

Do NOT allocate memory every frame.

Do NOT create:

    vector
    string
    texture
    shader
    COM object
    buffer

per frame unless absolutely unavoidable.

Allocate reusable resources once and reuse them.

Audit:

    new
    delete
    malloc
    free
    vector growth
    string construction

inside playback/rendering code.

============================================================
# 28. COM RESOURCE MANAGEMENT
============================================================

Use RAII.

Prefer:

    Microsoft::WRL::ComPtr

or an equivalent safe RAII wrapper.

Audit all:

    D3D11 resources
    DXGI resources
    Media Foundation objects
    textures
    surfaces
    device references

for lifetime leaks.

============================================================
# 29. MULTI-MONITOR SUPPORT
============================================================

Support multiple monitors.

Example:

    Monitor 1 -> video A
    Monitor 2 -> video B
    Monitor 3 -> video C

This may require multiple decoders.

However, share infrastructure wherever possible.

Share:

    D3D11 device
    DXGI factory
    shaders
    common renderer infrastructure
    configuration
    workload monitor

Do not duplicate them per monitor.

============================================================
# 30. SAME VIDEO ON MULTIPLE MONITORS
============================================================

This is a major optimization requirement.

If:

    Monitor 1 -> Video A
    Monitor 2 -> Video A
    Monitor 3 -> Video A

do NOT decode Video A three times.

Prefer:

    ONE decoder
       |
       v
    ONE playback timeline
       |
       v
    shared decoded frame
       |
       +----> Monitor 1
       +----> Monitor 2
       +----> Monitor 3

Scale/crop per monitor in the GPU.

============================================================
# 31. DIFFERENT VIDEO PER MONITOR
============================================================

If:

    Monitor 1 -> A
    Monitor 2 -> B
    Monitor 3 -> C

use only the required number of decoder pipelines.

Do not create extra decoder instances.

============================================================
# 32. PLAYLIST SYSTEM
============================================================

Support:

    single video
    playlist
    folder
    multiple folders
    loop
    shuffle
    sequential playback
    next video
    previous video

A playlist containing 10,000 videos must not require enormous RAM.

Store lightweight metadata:

    file path
    basic file metadata
    duration if cached
    resolution if cached
    codec if cached

Do not store decoded frames.

============================================================
# 33. VIDEO TRANSITIONS
============================================================

When Video A is ending and Video B is next:

Do not unnecessarily keep two complete playback pipelines alive.

Prefer:

    current decoder = active

and:

    next video = lightweight preparation

Only initialize the next decoder sufficiently early if profiling
shows that this significantly improves transitions.

Resource usage is more important than instant transition perfection.

============================================================
# 34. LOOPING
============================================================

For looping the same video:

Do not rebuild the entire rendering infrastructure.

Reuse:

    D3D device
    shaders
    textures where possible
    decoder infrastructure where possible
    metadata

Reset only the playback state.

============================================================
# 35. FRAME DROPPING
============================================================

If the decoder falls behind:

    drop obsolete frames.

Do not allow:

    frame 1
    frame 2
    frame 3
    ...
    frame 100

to accumulate.

Wallpaper playback does not require perfect archival frame delivery.

The current visible frame is more important than old frames.

============================================================
# 36. AUDIO
============================================================

Audio should be OFF by default.

Do not initialize audio playback unless explicitly implemented
as an optional future feature.

The default wallpaper engine should not consume resources
for audio.

============================================================
# 37. POWER MANAGEMENT
============================================================

The application must be battery-friendly.

Detect:

    AC power
    battery power
    display off
    system lock
    suspend/resume

Default behavior should favor resource conservation.

Possible default:

    pause wallpaper on battery

but make this configurable.

============================================================
# 38. LAPTOP GPU OPTIMIZATION
============================================================

Do not automatically force the discrete GPU.

On laptops:

    prefer the most power-efficient GPU capable of the task.

Do not wake an NVIDIA/AMD discrete GPU unnecessarily for
a simple wallpaper if the integrated GPU can efficiently
perform the task.

============================================================
# 39. GPU ADAPTER DETECTION
============================================================

Detect:

    GPU adapters
    outputs
    hardware decode capabilities

Select an appropriate adapter.

Do not blindly choose:

    "most powerful GPU."

The objective is:

    "lowest resource/power cost that provides reliable playback."

============================================================
# 40. PAUSED STATE
============================================================

When paused:

    stop decoder advancement
    stop frame scheduling
    stop unnecessary rendering
    stop performance-intensive monitoring
    clear obsolete frame buffers
    retain minimal state

If paused for a configurable long period:

    release decoder
    release temporary GPU resources
    release unnecessary frame buffers

Keep:

    current playlist position
    current file path
    configuration
    minimal state

============================================================
# 41. SUSPENDED STATE
============================================================

SUSPENDED means:

    almost nothing related to video playback remains active.

Target:

    no decoding
    no rendering
    no frame queue
    minimal timers
    minimal wakeups
    minimal GPU activity

The application should resemble a tiny background control process.

============================================================
# 42. SMART RESUME
============================================================

When playback becomes necessary again:

    initialize only what is required
    recreate decoder if necessary
    obtain current frame
    restart scheduler
    resume playback

Avoid repeated rapid initialization attempts.

Use controlled retry timing if hardware/media initialization fails.

============================================================
# 43. LOCK SCREEN
============================================================

When Windows is locked:

    stop video decoding
    stop rendering
    release unnecessary playback resources

When the user unlocks:

    resume according to configuration.

============================================================
# 44. DISPLAY OFF
============================================================

When a monitor/display is turned off:

    stop playback associated with it.

Do not decode video that nobody can see.

============================================================
# 45. MONITOR HOT-PLUG
============================================================

Handle:

    monitor connected
    monitor disconnected
    resolution changed
    refresh rate changed
    primary monitor changed

without requiring a reboot.

Do not leak D3D or window resources when a monitor disappears.

============================================================
# 46. WINDOWS EXPLORER RESTART
============================================================

Handle Explorer restarts where practical.

The wallpaper should recover without requiring the user to
manually restart the application.

============================================================
# 47. GPU DEVICE LOSS
============================================================

Handle Direct3D device loss/reset scenarios where practical.

Do not leave the application permanently broken after:

    GPU reset
    driver reset
    display topology change

Recreate resources cleanly.

============================================================
# 48. FILE ERROR HANDLING
============================================================

Handle:

    missing file
    deleted file
    moved file
    corrupt file
    unsupported codec
    unsupported container
    decoder initialization failure

Do not crash.

Skip invalid playlist entries where appropriate.

============================================================
# 49. LIBRARY SCANNING
============================================================

Do not scan the entire video library continuously.

Use:

    cached metadata
    filesystem change notifications
    incremental scanning

If a folder contains:

    10,000 videos

the application should not repeatedly enumerate all 10,000 files
every few seconds.

============================================================
# 50. THUMBNAIL SYSTEM
============================================================

If thumbnails are implemented:

    use small thumbnails
    use disk cache
    use bounded memory cache
    use LRU eviction

Do not keep thousands of full-size thumbnails in RAM.

When the library UI closes:

    release unnecessary thumbnail memory.

Thumbnail generation must NEVER interfere with active playback.

============================================================
# 51. BACKGROUND THUMBNAIL GENERATION
============================================================

Thumbnail generation must be:

    low priority
    throttled
    cancellable

If a game starts:

    stop thumbnail generation.

If the wallpaper is under heavy workload:

    stop thumbnail generation.

Never sacrifice the primary wallpaper performance goal for UI thumbnails.

============================================================
# 52. FILESYSTEM I/O
============================================================

Do not repeatedly touch the filesystem during normal frame playback.

Avoid:

    checking file existence every frame
    reading metadata every frame
    writing playback position every second
    writing logs continuously

Persist configuration only when necessary.

============================================================
# 53. LOGGING
============================================================

Release builds must have minimal logging.

Do not log every GPU operation.

Do not log every performance sample.

Implement:

    error logging
    warning logging
    optional debug logging

Example:

    maximum total log size = 5–10 MB

Do not allow logs to grow indefinitely.

# 68. PERFORMANCE MONITORING

# 99. MOST IMPORTANT PERFORMANCE REQUIREMENT
============================================================

Remember this throughout the entire project:

The application is NOT a game engine.

It is NOT a visual-effects engine.

It is NOT a media center.

It is NOT supposed to continuously render frames at the
maximum monitor refresh rate.

It is a wallpaper engine.

Therefore:

    Video = 30 FPS
    Monitor = 240 Hz

does NOT mean:

    render 240 unique video frames per second.

It means:

    decode the video at approximately the required rate,
    present frames appropriately,
    and avoid unnecessary work.
